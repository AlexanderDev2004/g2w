# hello-world example

A minimal g2w browser demo showing the **asset system**, the **scene system**, the **input system**, and the **2D sprite model**: the Effect-native `G2WGame` from `@g2w/runtime` (E4) drives a `PixiRenderer` from `@g2w/renderer-pixi` through the frame loop, a `SceneManager` switches between a **menu** scene and a **gameplay** scene, a DOM-free `InputState` fed by `@g2w/input-dom`'s `DomInput` provides keyboard, pointer, and touch input, and a DOM-free `GamepadState` sampled by `@g2w/input-gamepad`'s `GamepadInput` provides gamepad input, a texture asset manager from `@g2w/renderer-pixi` loads the local image, and the image is rendered through a core `Sprite2D`/`Transform2D` model driven by a `createSpriteView()` view from `@g2w/renderer-pixi`. This is a real Vite application — it uses only the public exports of the workspace packages.

## Run it

From the repository root:

```sh
pnpm install --frozen-lockfile
pnpm dev
```

Then open the printed local URL (for example `http://localhost:5173/`) in a browser. Vite serves the example with the workspace package sources aliased directly, so no prior build is needed.

## What it demonstrates

- `new G2WGame({ renderer, canvas, onUpdate, width: VIEW_WIDTH, height: VIEW_HEIGHT, resolution })` — constructing the Effect-native application runtime with the PixiJS adapter and a canvas. The width/height pair sets the logical resolution: the stage coordinate space game code uses, with the drawing buffer at `width×height×resolution`. The frame loop is the same synchronous, one-scheduler loop as core `Game` — the Effect runtime is involved only in lifecycle ownership, never per frame.
- `new SceneManager({ scenes, initial: "menu" })` — registering two scenes and starting with the menu.
- `new InputState()` + `new DomInput(input, { canvas, logicalSize: { width: VIEW_WIDTH, height: VIEW_HEIGHT } })` — the input path: a DOM-free state from `@g2w/core`, fed by real browser events from `@g2w/input-dom`. Touch contacts ride the same Pointer Events stream and feed the multi-touch contract keyed by `pointerId`; `pointercancel` releases stuck state. `new GamepadState()` + `new GamepadInput(gamepadState)` — the gamepad path (R5): an injectable polling source (the browser Gamepad API by default), sampled explicitly by `gamepadInput.poll()` once per frame. `logicalSize` maps pointer coordinates into the game's logical space so input stays correct when CSS scales the canvas display size.
- `createTextureAssetManager()` + `await assets.load("assets/g2w-logo.png")` — the asset path: the app creates and owns one texture asset manager from `@g2w/renderer-pixi`; the local image is loaded through the public asset API and shown in the gameplay scene. A second request for the same URL is served from the cache — the menu shows `texture cache: hit` to prove it.
- `new Sprite2D({ texture, transform: new Transform2D({ x, y }) })` + `createSpriteView({ sprite, renderer })` — the sprite path: game logic mutates the renderer-agnostic `Sprite2D`/`Transform2D` model and calls `logoView.sync()` once per change; the PixiJS adapter applies the transform to its display object. The gameplay scene animates the logo's rotation and scale purely through the model. The logo and sparks are **center-anchored** (`anchor: { x: 0.5, y: 0.5 }`, R11): position marks the sprite's center, so rotation spins each sprite around its own middle instead of its top-left corner. The logo's position was re-compensated for the anchor, so its on-screen placement is unchanged from before R11; the sparks were deliberately left uncompensated — their center coordinates are unchanged, so their visual placement shifts by half the (scaled) sprite size — because they orbit and spin continuously and spinning around the own middle is the point of the demonstration. The view is created once and reused across scene transitions — visibility is toggled through `logoModel.visible` plus `sync()`, so no sprite is duplicated.
- `onUpdate: (dt) => { gamepadInput.poll(); scenes.update(dt); input.endFrame(); gamepadState.endFrame(); }` — the active scene is updated by the existing game loop, the gamepad poll runs first so this frame's samples are what scenes read, and the edge states reset once per frame, after every consumer. There is no second loop and no hidden timer.
- In the **menu**: the pointer position (canvas-relative) is shown live, and a primary-button click transitions to gameplay — read through `input.wasButtonPressed(0)`, not a DOM click handler. The same click resumes the audio context and plays a short beep: `audioBackend.resume()` runs inside the click handler (a real user gesture, which is what the browser autoplay policy requires — playing against the still-suspended context would throw `WebAudioError` instead of failing silently), and the beep was decoded at startup, so the playback is a cache hit.
- `new AudioManager({ backend: new WebAudioBackend({ context: new AudioContext() }) })` + `await audio.load("assets/beep.wav")` — the audio path (R4): a core `AudioManager` over the `@g2w/audio-web` backend. Decoding works while the context is suspended; only playback needs the gesture-resumed context. Game logic plays through the public audio API and never touches `AudioContext` directly.
- In **gameplay**: the square is moved with WASD or the arrow keys (`input.isKeyDown`), a gamepad left stick (axes 0/1 with a demo-side 0.2 dead zone) or d-pad (buttons 12–15) (`gamepadState.getAxis`/`isButtonDown`), or a touch drag on the canvas (`input.activeTouchIds()`/`getTouchPosition`) — and `Esc` returns to the menu (`input.wasKeyPressed("Escape")`). The hint shows how many keys are currently held and whether a controller is connected.
- Startup order: assets are loaded first (`loading assets…` note until the texture arrives, and the error box if loading fails), then `await game.init()` initializes the renderer — `createSpriteView()` needs the initialized stage and is called right after — then `domInput.attach()`, `gamepadInput.attach()`, `scenes.start()`, `game.start()`.
- `game.addFinalizer(() => scenes.dispose())`, `game.addFinalizer(() => audio.dispose())`, and `game.addFinalizer(() => assets.dispose())` — the E4 ownership chain: the demo registers its resources as finalizers on the game, so `game.dispose()` alone releases them. Shutdown is LIFO: assets, then audio, then scenes (which destroy their display objects and the logo sprite view, never their textures), then the renderer. Every finalizer is attempted even if one fails, and failures stay observable through the `dispose()` rejection.
- `domInput.dispose()` and `gamepadInput.dispose()` on page teardown (`pagehide`) — the adapters first so no further events or samples reach the states, then `game.dispose()` once. Manager disposal never destroys textures from PixiJS's shared `Assets` cache (the page unload reclaims them). Audio disposal likewise never destroys decoded buffers explicitly — closing the context reclaims them.
- In dev mode only (`if (import.meta.env.DEV)`), the demo dynamically imports `@g2w/devtools` and opens the read-only overlay over the scene manager, the spark object collection, and the input state (with an explicit watch list). It is disposed first on `pagehide` — before the runtime it observes — and production builds (`pnpm build:example`) exclude it entirely.

PixiJS objects (texts, graphics, the logo sprite) are created at the adapter boundary: core scenes and game logic are renderer-agnostic and never touch PixiJS types. Ownership is split explicitly — scenes own and destroy their own display objects (texts, graphics), the sprite view owns only its display object (`logoView.dispose()` removes and destroys it but never the texture), the asset manager caches and deduplicates textures but never destroys them (they live in PixiJS's shared `Assets` cache until the page unloads), and the game owns the renderer plus every resource registered as a finalizer on it. There are no DOM event handlers in game logic — everything reads input through the framework API — no direct PixiJS `Assets` calls in game logic — everything loads through the public asset API — and no direct PixiJS sprite manipulation in game logic — everything renders through `Sprite2D`/`Transform2D` plus `createSpriteView()`.

If the game cannot start, the error is displayed on the page instead of failing silently.
